## Observations (non-blocking)

1. `recent()` reads `cache` without the mutex while `appendTurn` mutates it inside the mutex. Under genuinely concurrent turns (Ktor serves requests on multiple threads), an internal `ArrayList` read overlapping an append is a theoretical `ConcurrentModificationException` / stale-read window. The AC and both contracts only require the *writes* to be `Mutex`-serialized (satisfied), and this is a single-user parity app, so this is noted for the trail rather than blocking; if concurrency becomes in scope for T15 end-to-end, locking reads (or swapping in an immutable snapshot) would close it.
2. In `appendTurn`, the cache is mutated before the file append inside the lock. An `IOException` from `Files.writeString` would leave the cache ahead of the journal and propagate unclassified (route → generic masked 500 via `StatusPages`). Contract-silent; because the cache is the only read source, in-process context stays consistent — only the disk copy loses the turn.
3. The `ExposedSQLException` → 500 branch is reachable only if the real client lets tool exceptions travel out of its Koog execution path (Koog 1.3.0's session API exposes both `execute` and `executeUnsafe`). The catch list mirrors the AC exactly; T13/T14 integration should confirm DB-failure → 500 (and tool-loop break → 502) end to end with the real clients.
4. `KoogHttpClientException` — one of the three 502 mappings — has no dedicated test (gate 1 observation 1); the branch itself is trivially present in the catch list.
5. `userMessage` is matched with `any()` in every test (gate 1 observation 2); the seam order is verified by inspection here, so no contract risk, but a `slot` on that argument would pin it.
6. Journal truncation occurs at first `ChatService` resolution (Kodein singleton construction) rather than inside `AppModule.boot()`. Behaviorally equivalent for D-1: nothing reads the file, no append can precede construction, and singletons guarantee one construction per process — the previous run's transcript simply stays on disk until the first request (the design's crash-debuggability window).
