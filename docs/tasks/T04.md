# T04 - DI wiring

**Status:** `todo`
**Owner:** `backend-coder`

**Contracts:** `[CONTRACT-DI-001]`

## Description
Wire the Kodein composition per design §2 — `config` (AppConfig), `db` (4 named Databases), `logging` (masked logger), `service` (GetFuelingInfoTool), `client` (module declared; `local`/`remote` LlmClient bindings land with the D-16 branch task) — composed by `AppModule`; `Application.main` builds the graph, runs the fail-fast checks (config completeness → DB reachability → tool set) and starts Ktor on Netty.

## Acceptance Criteria
- [ ] `AppModule` composes the five modules from design §2; a DI smoke test resolves `AppConfig`, the four named `Database` bindings, the logging module's logger binding and `GetFuelingInfoTool` with no missing-binding errors.
- [ ] `Application.main` references only `AppModule` and contains no business logic, SQL, or LLM calls — `Application.kt` has no Exposed/Koog/service references (grep-verifiable; design §2).
- [ ] The server starts on Netty, binds port 8080, and answers HTTP: any request returns a Ktor response (e.g. 404), never a connection refusal (`curl -i http://localhost:8080/`).
- [ ] Fail-fast boot order works end-to-end with a non-zero exit and a clear message naming the cause for each case: a required `.env` key removed (e.g. `DB_PASSWORD`), one DB unreachable (`docker compose stop`), the tool JSON deleted (design §6).
- [ ] The `client` module exists in the composition with its `local`/`remote` named-binding seam declared but unimplemented; the graph still constructs without it (foundation scope — Koog client construction is a branch task).
- [ ] `./gradlew build ktlintCheck detekt` completes with 0 errors.
