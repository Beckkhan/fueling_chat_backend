# T13 - Koog LlmClient 'local' (Ollama)

**Status:** `done`
**Owner:** `backend-coder`
**Dependencies:** `[T12]`
**Contracts:** `[CONTRACT-LLM-001]`

## Description
Implement the `local` named binding of the pinned `LlmClient` seam (spec §3) with Koog 1.3.0 (D-16) on the `usual` branch: Ollama via its OpenAI-compatible endpoint, tool set passed in from `ChatService` per D-8 (never empty). `infrastructure.llm` references only Koog types and its own config — never service classes. Keep the turn assembly reusable so T14's DeepSeek client stays thin.

## Acceptance Criteria
- [ ] `OllamaLlmClient : LlmClient` constructed from `AppConfig` (`OLLAMA_BASE_URL`, `OLLAMA_MODEL`); the Koog HTTP-client factory is an injectable constructor parameter so tests can pass a `MockEngine`-backed factory.
- [ ] `run(systemPrompt, history, userMessage, tools)` assembles the Koog single-run turn: system prompt + history mapped by role (`user`/`assistant`), the service-supplied tool registry, `LLModel(LLMProvider.Ollama, config.ollamaModel)`, agent run returning the final text. The exact Koog 1.3.0 surface is verified against the pinned jars at implementation time (D-16); any wording deviation is documented in the correctness review.
- [ ] `ClientModule` binds `LlmClient` tag `local` to `OllamaLlmClient` (the `error()` stub is removed).
- [ ] The `OLLAMA_BASE_URL` default matches the verified endpoint surface of the pinned Koog version; the tracked `.env.example` line is updated if the default changes.
- [ ] `MockEngine` test (no Ollama running): a plain text reply yields the final text; a tool-call reply drives the agent loop — the fake tool's fixed text is sent back and the final answer returned, proving the service-supplied tool set is actually wired into the run (D-8); the outgoing request asserts the model id and the tool schema.
- [ ] `./gradlew build ktlintCheck detekt` completes with 0 errors.

## Scaffold

Pinned-jar verification performed at scaffold time (D-16, Koog 1.3.0 sources + bytecode from the Gradle cache):

- `OllamaClient.DEFAULT_BASE_URL = "http://localhost:11434"` (no `/v1` suffix) and the client posts to `<baseUrl>/api/chat` — the **Ollama native endpoint**, not the OpenAI-compatible `/v1/chat/completions`. The T13 description's "OpenAI-compatible endpoint" wording is a deviation; per the acceptance criteria it is documented here for the correctness review.
- **The current `OLLAMA_BASE_URL` default in AppConfig (`http://localhost:11434/v1`) is WRONG against the pinned jars and must be corrected to `http://localhost:11434`** — integrator-owned (AppConfig.kt, `.env.example`, and the `minimalEnvFileFallsBackToExampleDefaults` assertion in `AppConfigTest.kt` which pins the old default).
- Verified surfaces used by the scaffold: `PromptExecutor.builder().ollama(baseUrl, httpClientFactory)`; `KoogHttpClient.Factory` + `KtorKoogHttpClient.Factory(baseClient: HttpClient = HttpClient())` (http-client-ktor-jvm, on the classpath transitively; Koog 1.3.0 depends on Ktor 3.3.3 — the project's version, so `io.ktor:ktor-client-mock-jvm:3.3.3` aligns); `LLModel(provider, id, capabilities = null, ...)`; `LLMProvider.Ollama`; `prompt(id) { system(...); user(...); assistant(...) }`; `ToolRegistryBuilder().tools(List<ToolBase>)` accepts `List<Tool<*, *>>`; `AIAgentConfig(prompt, model, maxAgentIterations)`; top-level `AIAgent(promptExecutor, agentConfig, toolRegistry)` → `GraphAIAgent<String, String>` with `singleRunStrategy` (LLM → execute-tools → send-tool-results loop); `agent.run(userMessage)` appends the user message to the config-seeded prompt and returns the final text; outgoing request DTO `OllamaChatRequestDTO{model, messages, tools:[{type:"function", function:{name,description,parameters}}]}`; tool-call reply `message.tool_calls[].function.{name,arguments}`; tool results sent back as role `"tool"` messages; T14 reuse: `PromptExecutor.builder().addClient(DeepSeekLLMClient(apiKey, baseUrl))` (Koog `DeepSeekLLMClient` extends the Koog `LLMClient`).
