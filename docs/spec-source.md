# Проект Fueling Chat — единая спецификация

Сводный документ, объединяющий все требования, замечания и стандарты в последовательную структуру для production-grade fullstack-проекта с AI-оркестрацией.

---

## 1. Паспорт проекта

**Название:** fueling_chat
**Суть:** production-grade fullstack-приложение (React + Kotlin/Ktor) с AI-оркестрацией для работы с данными по проливам (fuelings) из Postgres. Пользователь через веб-чат с историей сообщений запрашивает детали по проливу по его ID; backend собирает данные из четырёх БД через tool и возвращает summary от LLM.

**Ключевая особенность:** проект выполняется **двумя независимыми способами в параллельных ветках**, с замером времени, токенов и качества, для сравнения архитектур агентной обвязки.

## 2. Функциональные требования

### Backend
- REST API для React-клиента.
- Эндпоинт чата: принимает `{prompt, fueling_id?, provider?}`, возвращает summary.
- История диалога хранится вне LLM (API stateless): in-memory кэш + текстовый файл; оба очищаются при рестарте.
- Метрика времени ответа и провайдера.

### Frontend (React)
- Чат с историей сообщений, поддерживающий уточняющие вопросы по проливу.
- Свитчер провайдера LLM: **local (Ollama)** ↔ **remote (DeepSeek)**.
- Реализация по макету Figma (Scandinavian Style Chat Design).

### LLM-оркестрация
- **Локальный провайдер:** Ollama (OpenAI-совместимый endpoint).
- **Удалённый провайдер:** DeepSeek (v4-pro для проектирования, v4-flash для кода в alternative-подходе).
- Routing в коде сервиса по полю `provider`, не в модели.

## 3. Технические требования

### Стек (безальтернативный)
- **Backend:** Kotlin + JVM (актуальный toolchain), Ktor (netty, content-negotiation, kotlinx-json)
- **DI:** Kodein DI
- **ORM:** Exposed поверх HikariCP (никакого plain JDBC и JPA)
- **LLM:** Koog-фреймворк (никаких рукописных HTTP-вызовов к LLM API)
- **Сериализация:** kotlinx-serialization-json
- **Логирование:** SLF4J + logback-classic; в коде — фасад `kotlin-logging` с ленивыми лямбдами
- **Тесты:** JUnit 5, MockK, kotlinx-coroutines-test
- **Стиль:** ktlint + detekt + `.editorconfig`
- **БД:** Postgres в Docker (`postgres:15-alpine`), 4 базы данных: `fueling`, `gas_station`, `payment`, `vendors`

### Архитектура
- Слои и направление зависимостей: `config ← infrastructure (db/client/logging) ← service ← routes`.
- Точка входа (`Application`) — только сборка модулей и wiring. Никакой бизнес-логики, SQL, LLM-вызовов.
- Fail-fast на старте: отсутствие кредов, недоступная БД, пустой набор инструментов — падение при запуске.
- Каждый модуль/агент владеет непересекающимся набором файлов.
- Нет лишних интерфейсов, избыточных абстракций и классов с минимальной логикой (R10).

### Dependency Injection (cdes-паттерн)
- Kodein-модули по слоям: `config`, `db`, `client`, `logging`, `service`.
- Все зависимости через `bind<T>() with singleton { }`.
- Несколько реализаций одного интерфейса — через именованные теги.
- Композиция в отдельном классе `AppModule`, не внутри `Application`.
- Глобальный держатель DI-контекста (`SharedDI`) допускается, если его кто-то читает.

## 4. Данные и схема

### Доступ к БД (через `.env`)
```
URL: jdbc:postgresql://postgres.stage.turboapp.ru:25432/postgres
host: postgres.stage.turboapp.ru
port: 25432
user: postgres
password: <DB_PASSWORD>
DEEPSEEK_API_KEY=<DEEPSEEK_API_KEY>
```

Локально Postgres поднимается в Docker через `postgres:15-alpine`.

### Четыре базы данных и их таблицы
- **`fueling`**: `fuelings` (partitioned by `created_at`, месячные партиции с 2025-01 по 2027-03), `fuelings_*` (партиции).
- **`gas_station`**: `gas_stations` (с координатами, брендом, лимитами).
- **`payment`**: `payments` (статусы, способы оплаты, суммы).
- **`vendors`**: `fueling_orders`, `fueling_events`, `vendor_fueling_orders`.

### Схема взаимодействия с данными (цепочка R9)
```
client → backend → LLM → tool → backend → БД
                ↑              ↓
                └── summary ← aggregated rows
```
- Tool описан в `resources/tools/get_fueling_info.json` (JSON-schema).
- Хэндлер tool'а исполняет SELECT через Exposed, собирает данные из 4 БД, возвращает агрегированный JSON.
- **Критично:** в каждом запросе к LLM поле `tools` — непустой массив.
- Tool работает только через backend с кредами из `.env`; **креды и SQL-доступ никогда не передаются в LLM** (DDL-first).

### Read-only гарантии
- Server-side `readOnlyMode=always` (клиентского флага HikariCP недостаточно).
- Никаких DDL/DML/миграций из кода приложения.
- Exposed-объекты = только структура; `SchemaUtils.create` запрещён в main-коде.
- Запросы возвращают сырые column-maps; JSON-колонки — текстом.
- Списки всегда с `LIMIT`, сортировка явная.

## 5. Требования к качеству

### Безопасность
- Креды БД и API-ключи **никогда не покидают backend**.
- `.env` не коммитится; в репозитории только `.env.example` с плейсхолдерами.
- LLM получает только DDL-файл со структурой таблиц, не доступ к БД.
- Маскирование в логах до записи: `DEEPSEEK_API_KEY`, `DB_PASSWORD`, `Authorization` (в т.ч. Bearer-форма), JSON-поля `api_key/password/secret/token`.

### Стиль кода
- **Комментариев минимум.** Запрещено: KDoc на тривиальных классах; комментарии перед очевидными функциями; повторение имени; объяснение синтаксиса.
- Разрешено: нетривиальная бизнес-логика, внешние контракты, обход багов библиотек, ссылки на Decision log.
- Лимиты: интерфейс ≤ 3 строк KDoc, класс ≤ 4, функция ≤ 2.
- Имена самодокументирующиеся: функция, требующая комментария, — переименовывается или декомпозируется.
- Функции ≤ 30 строк, ≤ 4 параметров. DTO — data class, иерархии — sealed class.

### Процесс ревью (4 гейта последовательно)
1. **correctness-reviewer** — логика, edge cases, контракты, DDL/DML-запрет, секреты.
2. **simplicity-reviewer** — дублирование, избыточные абстракции, мёртвый код.
3. **git-reviewer** — атомарность коммитов, формат сообщений, `.gitignore`.
4. **code-style-reviewer** — стандарт стиля, ktlint/detekt, автофикс форматирования.

**Важное дополнение для этого проекта:** агент-ревьюер **пишет результат каждого ревью в файл** (например, `reviews/T<n>-<reviewer>.md`), чтобы позже можно было объективно сравнить качество кода в ветках `usual` и `alternative`.

### Вердикт-only для сборок и тестов
- Любой `./gradlew build` или `./gradlew test` читается **только по финальному вердикту** (`--quiet` или `2>&1 | tail -N`).
- При провале читается только секция ошибок (grep по `FAILED`/`Exception`).
- Полный вывод не читает никто и никогда — это сжигает критическое количество токенов.

### Экономика токенов в агентной обвязке
- Промпт на запуск агента: строка задачи + критерии приёмки + **ссылки на контракты по ID** (агент сам читает секцию спеки). Дословный текст контрактов и содержимое определений агента не повторяются.
- Каждая строка бэклога несёт список ID контрактов, от которых зависит задача.
- Возврат задачи = возобновление того же агента с сохранённым контекстом + список замечаний, не пересоздание.
- Оркестратор (CTO) **не отслеживает streaming-процесс** работы агентов: только вердикты в формате `T<n> done | verified: ok`.
- Агенты общаются через файлы (задача → артефакт → вердикт), не через диалог.

## 6. Мультиагентный процесс

### 6.1 Фазы работы (строго последовательно)
1. **Фаза дизайна** — `system-design` skill превращает идею в `<project>-design.md`. Hard-gate: без утверждённого дизайна никакой реализации, спецификации и scaffold'а.
2. **Фаза спецификации** — спецификация с контрактами, журналом решений, DDL-файлом.
3. **Фаза декомпозиции** — каждая задача в **отдельном файле** (не в едином `tasks.md`), с владельцем, артефактом, зависимостями, контрактами.
4. **Фаза реализации** — `/process` запускает исполнение задач последовательно через CTO.
5. **Фаза ревью** — 4 гейта на каждую задачу; результаты сохраняются в файлы.
6. **Фаза замера** — агрегация метрик времени и токенов, сравнение подходов.

### 6.2 Команды и роли
- **CTO** — оркестратор, единственный хаб, единолично владеет статусами.
- **Команда проектирования** (plan, design, tasks) — создаёт документацию.
- **Команда реализации** — кодинг-агенты, выполняют задачи.
- **Команда тестирования** — тесты и ревью.
- **`system-design` skill** — на уровне пользователя (не проекта); spawn'ится в начале работы над проектом.

### 6.3 Структура папок
- `.claude/agents/<team>/<agent>.md` — определение агента.
- `.claude/agents/<team>/<agent>/skill.md` — ремесло и контракты агента.
- `docs/` — спецификации, дизайн, DDL, задачи.
- Каждая задача — отдельный файл (`docs/tasks/T<n>.md`), а не строка в общем списке.

### 6.4 Звёздная топология (hub-and-spoke)
- CTO — единственный хаб; агенты не общаются между собой напрямую.
- Контексты агентов изолированы; общие — файловая система, бэклог, спецификация.
- Контракты замораживаются до реализации; в рантайме не обсуждаются.
- Пробелы спецификации эскалируются в spec-команду; inline-починка запрещена.

## 7. Два подхода реализации (эксперимент)

### Стратегия ветвления
```
main (master) ──┬── usual      ── реализация подходом №1 (backend + frontend)
                │
                └── alternative ── реализация подходом №2 (backend + frontend)
```
- **Одинаковый старт:** обе ветки ответвляются от `main` после закладки общего фундамента (scaffold, DI, схема БД, базовые контракты).
- Параллельные ветки для backend и frontend в обоих подходах.

### Подход `usual` (базовая обвязка)
- Полная мультиагентная обвязка с **одним кодинг-агентом** на задачу.
- Агент пишет полный код от начала до конца.
- Все 4 ревью-гейта проходят как обычно.

### Подход `alternative` (dual-coder)
- **Два кодинг-агента вместо одного:**
    1. **coder-architect** (модель `deepseek-v4-pro`, сильная): пишет **каркас кода** — сигнатуры методов и комментарии с описанием логики метода (TODO-блоки с тем, что должен делать метод), без реализации.
    2. **coder-implementer** (модель `deepseek-v4-flash`, быстрая): берёт сгенерированный каркас и **наполняет сигнатуры кодом** согласно TODO-комментариям.
- Ревью-гейты — те же 4, но применяются к финальному результату (после работы coder-implementer).

### Гипотеза эксперимента
- `usual`: меньше агентов, проще координация, но одна модель несёт всю нагрузку (дороже по токенам на генерацию, возможно хуже по качеству при длинных задачах).
- `alternative`: дорогая модель используется только для архитектурных решений, дешёвая — для рутины; потенциально ниже стоимость и выше качество за счёт разделения ответственностей, но выше координационные издержки.

## 8. Метрики эксперимента

### Что замеряется по каждой ветке (backend + frontend отдельно)
- **Wall-clock время** выполнения всех задач от старта `/process` до последнего `verified: ok`.
- **Суммарные токены** на всё выполнение (включая ревью, хэндбэки, повторные прогоны).
- **Количество хэндбэков** от reviewer'ов к owner'ам.
- **Количество findings по каждому гейту** (читается из сохранённых файлов ревью).

### Артефакты замера
Отдельный файл **`comparison-report.md`** в корне проекта, содержащий:
1. Таблицу метрик: время и токены для backend и frontend в обоих подходах.
2. Краткое резюме:
    - **Какой подход оптимален по затратам времени и токенов** — с цифрами и выводами.
    - **Оценка качества кода** в обоих случаях:
        - В каком подходе было больше багов.
        - В каком подходе код получился чище (меньше замечаний от reviewer'ов).
        - Сравнение по каждому из 4 гейтов.
    - Выводы: когда какой подход применять в будущих проектах.

### Источники данных для сравнения
- `reviews/T<n>-<reviewer>.md` — детальные findings каждого ревью.
- Логи оркестратора — время и токены на задачу.
- Финальные артефакты (код) — для субъективной оценки читаемости.

## Краткое резюме структуры

1. **Что строим** (§1–2): fullstack-приложение с AI-оркестрацией и двумя параллельными подходами.
2. **На чём** (§3–4): Kotlin/Ktor/Koog/Kodein/Exposed + React; 4 базы Postgres.
3. **Как качественно** (§5): минимум комментариев, 4 ревью-гейта, verdict-only, экономия токенов.
4. **Как работаем** (§6): system-design → спецификация → задачи → `/process` → ревью → замер; звёздная топология с CTO во главе.

6. **Что считается готовым** (§9–10): чек-лист приёмки и список артефактов.

Документ самодостаточен — его можно передать в `system-design` skill как входной контекст, после чего процесс пойдёт по зафиксированной цепочке фаз.
