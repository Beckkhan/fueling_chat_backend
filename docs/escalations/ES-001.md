# ES-001 — Spec gap: tool-loop exceptions never reach the service classification seam

**Escalated by:** CTO (execution-only pipeline, `first` branch)
**Date:** 2026-10-13
**Source:** `reviews/T13-correctness-reviewer.md`, finding F1 (PASS verdict, not charged to the T13 diff)
**Status:** open — awaiting Specification team decision

## Gap

Koog 1.3.0's `GenericAgentEnvironment.processToolCall` catches tool-execution exceptions **below** the pinned `LlmClient` seam and converts them into an error tool result for the model. Consequences:

1. An `ExposedSQLException` thrown by `GetFuelingInfoTool` never reaches `ChatServiceImpl`'s `ExposedSQLException → ChatFailure(500, "Databases unavailable")` branch (CONTRACT-SERVICE-001). Instead the turn returns 200 with a model-written summary, or 502 if the model retries to the iteration cap. CONTRACT-API-002 requires 500 on any DB failure.
2. `ExposedSQLException.message` embeds the failing SQL. Koog sends the error tool result to the LLM (local Ollama today; external DeepSeek after T14) and logs the throwable — the logback TurboFilter cannot rewrite it. This contradicts spec §4 / design §3 step 10 (no raw SQL to the model or logs).

No fix exists inside T13's artifacts — Koog catches below the seam.

## Options for the Specification team (from the correctness review)

- (a) Accept as a documented deviation (200 + model explanation on DB failure).
- (b) `GetFuelingInfoTool` catches `ExposedSQLException` itself and returns a sanitized JSON error (same 200, no SQL leak).
- (c) Re-scope the 500 row of CONTRACT-SERVICE-001 / CONTRACT-API-002.

CTO made no decision and changed nothing: per execution-only mode, gaps are escalated, never fixed inline. This blocks T15's end-to-end acceptance (DB-failure behavior) until resolved.
